# PSCV0 v7 vs Lean 4.35.0-rc4 — Source-level architecture and implementation review

**Audit date:** 13 October 2026. **Scope:** PSCV0 compiler as checked into the public branch, compared with pinned Lean 4.35.0-rc4 source and its reference documentation. **Assessment, not a claim of feature completion or formal correctness.** This audit is a documentation-only checkpoint and does not change compiler behavior.

**Repository:** [dwijayuda/pskernel](https://github.com/dwijayuda/pskernel); **branch:** `psc0/pscv0-v7-native-lean-v1`; **draft PR:** [#109](https://github.com/dwijayuda/pskernel/pull/109).

**Audited PSCV0 source HEAD:** `1cc7deb56b2b6ec37ee3a6c1eac148d113899ac7`. **Most recent green executable checkpoint:** `e1d463e10cbf5edd817e362ed35b21ee82c8c85b`, [Linux CI 38304955212](https://github.com/dwijayuda/pskernel/actions/runs/38304955212). **Current source CI:** [38307096314](https://github.com/dwijayuda/pskernel/actions/runs/38307096314) — **FAILED**. **Upstream Lean source:** `c29b6dda4f7c20e3eeaa717c4e565663c5cfa364`, official 4.35.0-rc4. Don't conflate a documentation HEAD with executable qualification. Re-query branch HEAD and CI when continuing.

## Executive assessment

**Conclusion:** PSCV0 has a defensible *architecture for an independent, selected language plus multiple target backends*, and it correctly relies on the official Lean kernel for the admitted Core declaration boundary. However, PSCV0 is **not** equal to Lean 4 in the quality, coverage, completeness, optimization or diagnostic maturity of its elaborator, recursive definitions, Standard universe, proof automation, compiler lowering, incremental build graph or runtime. Current CI exposes a structural, not cosmetic, issue: dependent / Prop-valued index arguments survive erasure as unrepresentable runtime types and the IR checker correctly refuses them.

**Do not weaken** the IR checker, relabel `.unknown` as a legal runtime type, silently replace proof validity with a Boolean, reinterpret panics as defaults, or bypass official kernel admission. Close the common binder-classification and type-erasure contract first. PSCV0's potential differentiators are **verification-gated emission, direct JS/TS/Rust/Wasm GC and Canonical ABI targets, source-level developer ergonomics, and trustworthy AI/software-factory integration**; these are differentiated *design goals*, not all qualified capabilities today.

## 1. Side-by-side implementation pipeline

|---|---|---|---|
| Parser | Extensible token/Pratt tables, macro grammar, ordered command parser; changes to syntax environment affect following commands | Dedicated pure token / PSCV0 parser and fixed term/proof/do readers, explicit source spans, confined surface | Simpler and more constrained, but not Lean's generic extension ecosystem |

## 2. Trust model and semantic fidelity

PSC0 **does not use pskernel-core** for v7. Its checked native host decodes canonical prepared declarations and calls the pinned official Lean `Environment.addDeclCore` with checking enabled; only then does the host attempt erasure and emission ([source](https://github.com/dwijayuda/pskernel/blob/1cc7deb56b2b6ec37ee3a6c1eac148d113899ac7/psc0/host/src/Ps/Host/NativeV7.lean#L60-L124)). This is a major correctness-positive design decision.

**Important distinction:** the official checker validates the submitted declarations *relative to the reconstructed PSC prelude*. It does not by itself prove that .ps parsing preserves every Lean source meaning, or that resulting JS/TS/Rust/Wasm code executes with that meaning. The [provider prelude adapter](https://github.com/dwijayuda/pskernel/blob/1cc7deb56b2b6ec37ee3a6c1eac148d113899ac7/psc0/packages/pskernel-lean/provider/PsKernelLean/Prelude.lean#L59-L173) converts PSC axioms and definitions into Lean declarations. The [primitive audit](https://github.com/dwijayuda/pskernel/blob/1cc7deb56b2b6ec37ee3a6c1eac148d113899ac7/psc0/host/src/Ps/Host/PrimitiveAudit.lean#L27-L81) compares signatures, explicitly labels runtime primitive bodies as assumptions, and accepts reviewed portable-model differences for several `Array`, `String.Pos.Raw`, and `Prod` signatures. That is an honest audit, **not a proof of semantic equivalence**.

The public name `psCompilerVerifiedIrFromPrepared` can mislead: [the function](https://github.com/dwijayuda/pskernel/blob/1cc7deb56b2b6ec37ee3a6c1eac148d113899ac7/psc0/packages/compiler/src/Ps/Compiler/Api.lean#L277-L330) constructs typed IR from an admission-ready module, without carrying a nonforgeable kernel-check token as an API input. In the qualified native host the preceding kernel gate is explicit; other entry points must not infer that the method name itself proves admission. Recommend a provider-neutral checked-session / ephemeral typed handle that can be created only after the official check, while keeping IR well-formedness as a separate gate.

Lean's own compiler is not a general semantics-preservation proof either; kernel acceptance protects proofs and types, not the correctness of emitted native code. Full verified executable semantics requires additional target/refinement evidence in PSCV0 as designed.

## 3. Why GetElem currently fails after Lean checks succeed

**Current failure evidence:** [Linux run 38307096314](https://github.com/dwijayuda/pskernel/actions/runs/38307096314) at `1cc7deb56b2b6ec37ee3a6c1eac148d113899ac7` reports:

```text
proof-carrying GetElem source not accepted: ir/emit:
PSCV0-IR-CHECK: indexBoxGet:root/resultType: unknown-type annotation
indexBoxGet:root/body/typeArgument3: unknown-type annotation
indexBoxGet:root/body: unknown-type equality-left
implicitLookup:root/body/.../typeArgument3: unknown-type annotation
```

This follows earlier transitions: after adding the official Lean oracle and JS/TS/Rust emission test, native checks first refused missing `GetElem.mk` in the runtime closure, then an unsupported erased type-family term, then the present IR type mismatch. These are **unqualified attempts**; they do not undo the earlier green checked-source milestone.

The type model is central. `PsVerifiedIrType` has `unknown`, primitive, type parameter, function and named forms ([model](https://github.com/dwijayuda/pskernel/blob/1cc7deb56b2b6ec37ee3a6c1eac148d113899ac7/psc0/packages/compiler-ir/src/Ps/CompilerIr/Model.lean#L1-L30)); the IR validator *properly rejects unknown* as a runtime annotation or equality input ([validator](https://github.com/dwijayuda/pskernel/blob/1cc7deb56b2b6ec37ee3a6c1eac148d113899ac7/psc0/packages/compiler-ir/src/Ps/CompilerIr/CheckTypes.lean#L68-L110)). PSCV0's [eraser](https://github.com/dwijayuda/pskernel/blob/1cc7deb56b2b6ec37ee3a6c1eac148d113899ac7/psc0/packages/erasure/src/Ps/Erasure/Expr.lean#L21-L84) currently turns every binder classified as `.type` into an IR type argument, but `GetElem.valid : coll → idx → Prop` is a dependent **predicate family**, not a representable runtime type. [Type erasure](https://github.com/dwijayuda/pskernel/blob/1cc7deb56b2b6ec37ee3a6c1eac148d113899ac7/psc0/packages/erasure/src/Ps/Erasure/Basic.lean#L639-L770) can produce `.unknown` for these higher-order or unreifiable terms.

This is **a mismatch between compile-time parameter kinds and runtime types**. Correct architectural redesign:

1. Normalize/check a full Core telescope and assign each binder an **explicit, checked role**: runtime value, runtime-reifiable type, erased proof, and erased dependent/type-level index (including `Prop` families).
2. The same role/arity map must drive declaration signatures, instance dictionaries, application lowering, structure fields/projections, IR typing, specialization, ABI planning, source/provenance and assumption/erasure ledger. Avoid per-backend heuristics.
3. Do not materialize the erased `valid` predicate as `PsVerifiedIrType.unknown`; retain only required runtime-reifiable generics in the executable IR. Preserve enough non-runtime evidence to check that erased values are not consumed at runtime.
4. Derive consistent typed IR signatures once, then validate both their erased calling convention and all generated usages. Fail closed for higher-order indexes the selected runtime cannot preserve. Check the official Lean admission **before** emitting.
5. Qualify first on user-defined `GetElem` proof cases (including `i = 0`, `True`, `True ∧ True`), then polymorphic dependent dictionaries, nested calls and modules; only then expand real List/Array/`Fin`.

Merely teaching the IR checker that `.unknown` is acceptable would hide this bug rather than fix it.

## 4. Elaborator and typeclass comparison

Lean's [`SynthInstance.lean`](https://github.com/leanprover/lean4/blob/c29b6dda4f7c20e3eeaa717c4e565663c5cfa364/src/Lean/Meta/SynthInstance.lean#L1-L190) uses **tabled resolution**: normalized goal keys, generator and consumer nodes, reusable answers and waiters, instance-size and heartbeat limits, and optimizations for canonical instances. The [synthetic metavariable solver](https://github.com/leanprover/lean4/blob/c29b6dda4f7c20e3eeaa717c4e565663c5cfa364/src/Lean/Elab/SyntheticMVars.lean#L573-L649) repeatedly revisits pending unification/typeclass/tactic constraints after new information appears; failure is reported when no progress can be made.

By contrast, [`Ps.Meta.SynthInstance`](https://github.com/dwijayuda/pskernel/blob/1cc7deb56b2b6ec37ee3a6c1eac148d113899ac7/psc0/packages/meta/src/Ps/Meta/SynthInstance.lean#L256-L389) recursively enumerates candidates with immutable constraint snapshots, output-key masking, active-path cycle detection and hard-coded fuel 64. These are legitimate robustness safeguards, but there is **no equivalent answer table or suspended-consumer dependency graph**. [`Ps.Meta.Unify`](https://github.com/dwijayuda/pskernel/blob/1cc7deb56b2b6ec37ee3a6c1eac148d113899ac7/psc0/packages/meta/src/Ps/Meta/Unify.lean#L90-L165) is a fuel-bounded bespoke unifier with weak-head normalization, not Lean's full constraint-resolution architecture.

**Verdict:** quality is good for a deliberately selected subset, but not equal to Lean for complex higher-order inference, polymorphic overlapping instances, recursion through typeclass dependencies, performance or error explanations. The next clean redesign is a tabling and suspension architecture, not adding more instance-specific fixes.

## 5. Inductives, strict positivity and recursion

Lean elaborates general inductives in [`Elab/Inductive.lean`](https://github.com/leanprover/lean4/blob/c29b6dda4f7c20e3eeaa717c4e565663c5cfa364/src/Lean/Elab/Inductive.lean), mutual/recursive declarations in [`Elab/MutualDef.lean`](https://github.com/leanprover/lean4/blob/c29b6dda4f7c20e3eeaa717c4e565663c5cfa364/src/Lean/Elab/MutualDef.lean), and checks inductive safety in the trusted C++ [`kernel/inductive.cpp`](https://github.com/leanprover/lean4/blob/c29b6dda4f7c20e3eeaa717c4e565663c5cfa364/src/kernel/inductive.cpp). The kernel does **not** itself run a high-level syntactic termination checker; elaboration converts accepted recursion into core recursor/well-founded forms that the kernel checks (see official [Elaboration and Compilation reference](https://lean-lang.org/doc/reference/latest/Elaboration-and-Compilation/)).

[PSC0 `Ps.Elab.Data`](https://github.com/dwijayuda/pskernel/blob/1cc7deb56b2b6ec37ee3a6c1eac148d113899ac7/psc0/packages/elab/src/Ps/Elab/Data.lean#L32-L134) allows selected positive direct occurrences and allowlisted nested containers such as `List`, `Option`, `Array`, `Prod`, refusing unknown shapes. [`Ps.Elab.Recursion`](https://github.com/dwijayuda/pskernel/blob/1cc7deb56b2b6ec37ee3a6c1eac148d113899ac7/psc0/packages/elab/src/Ps/Elab/Recursion.lean) handles selected structural recursion and call rewriting. This intentionally rejects many legal Lean patterns (mutual/well-founded, broader indexed or nested families), but is better than admitting arbitrary recursion. **Current incompleteness is predominantly false rejection, not evidence of false acceptance.** Any inferred safety claim still depends on official kernel checking of the final declarations.

Recommended architecture: represent an elaborated inductive block and shared positivity/recursor plan rather than per-constructor special rules. For termination, use one explicit obligation object and a lowering to well-founded recursors, with no `partial`/ `unsafe` escape in verified mode. Reuse official Lean proof services selectively where possible instead of attempting to reproduce all of Lean's automation.

## 6. Proofs, typed do, contracts and verification

Lean has a general tactic framework, proof producing `simp`/`omega`/`grind`, rewriting and elaborator extensions. PSCV0's [`Ps.Elab.Proof`](https://github.com/dwijayuda/pskernel/blob/1cc7deb56b2b6ec37ee3a6c1eac148d113899ac7/psc0/packages/elab/src/Ps/Elab/Proof.lean) implements selected `exact`, `refine`, `apply`, `intro`, `assumption`, `rfl`, `constructor`, cases/induction and goal control. The now-green `GetElem` tactic is soundly **goal-closing and fuel-bounded** for assumption, rfl, and recursive trivial constructors. It does not have Lean `omega`/ `simp` parity.

Crucially [`Ps.Elab.Do`](https://github.com/dwijayuda/pskernel/blob/1cc7deb56b2b6ec37ee3a6c1eac148d113899ac7/psc0/packages/elab/src/Ps/Elab/Do.lean#L7-L81) currently has explicit `identity`, `option`, `except` effect variants rather than fully generalized class-driven `Monad`/`State`/`Reader`/transformers. This is an architectural debt, not proof that `do` is complete. Remaining `given`/`requires`/`ensures`/WP/VC/invariants/effect/assumption-ledger support is a major unfinished verification goal.

**Differentiating opportunity:** PSCV0 proposes two assurance outcomes for one language: ordinary checked executable vs verified executable, where verified emission is forbidden if mandatory proof, spec coverage, effect, assumption, termination or erasure obligations remain. This is worth preserving, but **there is no completed verified-emission gate yet**. Do not describe ordinary Lean kernel admission as successful verification of all requested software behavior.

## 7. Backend quality, performance and runtime correctness

Lean's [LCNF compiler](https://github.com/leanprover/lean4/blob/c29b6dda4f7c20e3eeaa717c4e565663c5cfa364/src/Lean/Compiler/LCNF/Main.lean#L191-L227) uses base, monomorphized, post-lambda and impure phases, SCC decomposition, configurable pass management, checkpoints, low-level IR conversion, allocation/refcount analysis and native emission; [explicit RC passes](https://github.com/leanprover/lean4/blob/c29b6dda4f7c20e3eeaa717c4e565663c5cfa364/src/Lean/Compiler/LCNF/ExplicitRC.lean) and a mature [C++ runtime](https://github.com/leanprover/lean4/blob/c29b6dda4f7c20e3eeaa717c4e565663c5cfa364/src/runtime/object.cpp) manage memory and execution.

PSC0 uses a shared checked `PsVerifiedIr`, [IR specialization](https://github.com/dwijayuda/pskernel/blob/1cc7deb56b2b6ec37ee3a6c1eac148d113899ac7/psc0/packages/compiler-ir/src/Ps/CompilerIr/Specialize.lean), [well-formedness/type checking](https://github.com/dwijayuda/pskernel/blob/1cc7deb56b2b6ec37ee3a6c1eac148d113899ac7/psc0/packages/compiler-ir/src/Ps/CompilerIr/Check.lean), [JS emitter](https://github.com/dwijayuda/pskernel/blob/1cc7deb56b2b6ec37ee3a6c1eac148d113899ac7/psc0/packages/backend-ecma/src/Ps/BackendEcma/Lower.lean), [Rust emitter](https://github.com/dwijayuda/pskernel/blob/1cc7deb56b2b6ec37ee3a6c1eac148d113899ac7/psc0/packages/backend-rust/src/Ps/BackendRust/Module.lean), and [Wasm GC / Canonical ABI backend](https://github.com/dwijayuda/pskernel/blob/1cc7deb56b2b6ec37ee3a6c1eac148d113899ac7/psc0/packages/backend-wasm/src/Ps/BackendWasm/Module.lean). These boundaries are clean and potentially valuable, particularly for multi-platform portability. However, **no benchmark shows equal or superior optimization quality to Lean** and the new dependent `GetElem` source is currently blocked by IR typing.

A specific complexity issue exists already: PSCV0's `List.take/drop` implement their selected functions using `List.rec` with a Nat-indexed result worker ([`StandardList.lean`](https://github.com/dwijayuda/pskernel/blob/1cc7deb56b2b6ec37ee3a6c1eac148d113899ac7/psc0/packages/environment/src/Ps/Environment/StandardList.lean)). Lean's [`List.take/drop`](https://github.com/leanprover/lean4/blob/c29b6dda4f7c20e3eeaa717c4e565663c5cfa364/src/Init/Data/List/Basic.lean#L897-L935) recurse together over count and list and can stop at the selected prefix. Lean also has a `takeTR` runtime implementation with a proven `@[csimp]` equivalence ([source](https://github.com/leanprover/lean4/blob/c29b6dda4f7c20e3eeaa717c4e565663c5cfa364/src/Init/Data/List/Impl.lean#L194-L219)). PSC's current algorithm may do unnecessary traversal for small counts; the provable complexity and performance parity are **not established**. A direct total worker or separately proved specialization is preferable over a compiler-wide workaround.

Do not collapse linear-memory-only MVP compatibility into Wasm GC internals without a specific target requirement. Keep source values in Wasm GC and use linear memory at explicit Canonical ABI interface boundaries, as already required.

## 8. Modules, provenance, diagnostics and developer tooling

Lean's [command frontend](https://github.com/leanprover/lean4/blob/c29b6dda4f7c20e3eeaa717c4e565663c5cfa364/src/Lean/Elab/Frontend.lean#L64-L105) processes parse/elab commands against a changing environment, supports incremental snapshots, and surfaces rich info trees, hover/goal information and `.olean` interfaces. PSCV0's [project planner](https://github.com/dwijayuda/pskernel/blob/1cc7deb56b2b6ec37ee3a6c1eac148d113899ac7/psc0/packages/compiler/src/Ps/Compiler/Pscv0Modules.lean#L206-L276) orders imports, supports public/private visibility and diamonds, tracks provenance, rejects unavailable names and prepares a checked closure. This is genuine progress, but **not** complete Lean module fidelity: no equivalent mature incremental red/green query graph, generated-code caching or IDE data service is qualified yet. Keep C5 reconstruction deferred while core semantics remain unfinished.

## 10. Prioritized implementation architecture

**P0 — Repair typed erasure as a whole feature family.** Define a compositional binder-role/telescope classification; preserve runtime-reifiable types, erase proof and predicate/type-level indices, and use one exact signature/arity map from Core to IR to every backend. Refuse unsupported dependence; never relax `unknown-type`. Qualify user-defined GetElem on native official Lean, emitted JS/TS/Rust/Wasm code, and corresponding runtime observations. Fix the native CI first, then record a new **qualified** SHA.

**P1 — Complete one faithful GetElem/GetElem? vertical slice.** Implement Lean RC4 superclass relationships, `LawfulGetElem` checked equations, decidability, `Option` universe generalization, `i < length/size` as real Prop, proof-carrying `List`/`Array`/`Fin` access, exact optional semantics and observable panic/default contract. Add `omega`/simp-based *proof construction*, not unverified Bool conversion. Stop before accepting syntactic `?`/`!` as fully supported.

**P2 — Mature the elaboration engine.** Build tabled instance search with normalized keys and suspended consumers, delayed elaboration/universe/TC constraints, error provenance, deterministic resource budgets, and explicit transaction/backtracking states. Compare behaviour and resource use against pinned `Lean.Meta.SynthInstance` and `Lean.Elab.App` rather than continually patching cases.

**P3 — Dependent data and checked total recursion.** Complete uniform parameter/index motives, positivity proof/validation, selected mutual and well-founded recursion, internal recursor sharing, and runtime layout/erasure. Preserve official kernel check as the mandatory final boundary.

**P4 — General typed effects and specifications.** Replace closed `DoOps` variant selection with class-driven bind/pure/transformer resolution, effects/IO capability boundaries and a centralized WP/VC/effect/assumption/erasure obligation ledger. **P5 — Performance and full conformance evidence.** Differential official Lean RC4 positive/negative cases; explicit backend semantics for every selected primitive; cost/alloc/stack/warm/cold compilation benchmarks; SSA-like and LCNF-inspired optimization phases only where measurements justify them; true multi-module conformance and stable import/notation/tactic/effect/axiom manifest. Close P0–P5 before final Phase E and before claiming equal or better quality.

### Testing discipline

Implement **coherent architectural capabilities before broad testing**, with early small oracle cases only when a critical typing, erasure, safety or universes invariant is unknown. Every acceptance milestone needs: (1) exact reviewed source SHA and official Lean version, (2) positive kernel admission, (3) minimal negative refusal at correct stage, (4) IR completeness with **no unknown runtime types**, (5) deterministic multi-target output/behavior, (6) the full existing 187-observation regression, and (7) updated frozen environment/trust evidence if the Standard roster changes. Do not invent acceptance percentages or call an unqualified HEAD green.

## Bottom line

**Keep PSCV0 independent for its selected language and verified multi-backend design; do not try to make the entire Lean elaborator, tactics, Standard library and optimizer a second codebase by incremental special cases.** Borrow and, when sensible, integrate Lean's proven architectural ideas and official proof tooling. Design proof interoperablity as a clean checked-term/import interface without requiring `pskernel-core` or self-hosting now. Preserve native portable `.lean`, Wasm GC + Canonical ABI boundaries, branch history, and full source/assumption provenance. The immediate progress indicator is **green dependent typed IR emission**, not another expanded parser feature list.
