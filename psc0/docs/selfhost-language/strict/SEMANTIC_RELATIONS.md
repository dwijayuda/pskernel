# Shared semantic relations for strict PSC0-SH/1

## Status and authority

This document gives a common vocabulary, concrete evaluation rules, and an inventory of the actual binder and substitution paths for the enabled source/Core → original IR → TypeScript/JavaScript argument. Its source boundary is commit `2b5a4c903ed8a069cde8f08265b28042bcaf5766`. It is a documentation candidate for independent review. It changes neither the language contract nor implementation behavior.

There are three different kinds of statement here:

- **Definition:** a mathematical relation or invariant to be used consistently by the rule arguments.
- **Source case fact:** a stated structural property follows from the enumerated branches of the pinned functions. The proof given is a paper argument about those branches, with any imported premise named.
- **Open semantic obligation:** a preservation, adequacy, or completeness statement whose hypotheses have not all been established. Stating such a lemma does not discharge it.

No formal theorem is added or claimed. All 33 N/ER/EV/TS rows in the committed correspondence ledger remain open. In particular, `strictSh1Qualified`, `semanticContractQualified`, `generalPreservationProven`, and `formalPreservationProven` remain false. A successful exact-source qualification, an original-IR typing result, a fixed point, and provider admission each have their existing separate scope. None establishes the relations below by itself. [S01–S04]

The normative source is SPEC, especially its source-origin, normalization, erasure, runtime, and conformance requirements. Handwritten PSC1-compatible `.lean` remains authoritative; generated `.ps` remains new-only `ps-0.9-r3`. R stays selected. The native reference is Lean 4.34.0 at `293d5d0c0c3f3dded4688b3ccd6a33939ac5102b`; the JavaScript lane is TypeScript 7.0.2 and Node 22.23.3. Kernel, provider, definitional equality, caches, and existing theory are outside this change. [S01–S06]

SPEC requires truthful retained origins and a defensible general semantic argument. It does not require a new serialized Core-to-IR certificate. A proof over actual reachable compiler states is a valid route. A separately checked per-compilation witness is another route, with its own checker-correctness obligation. The mathematical witnesses below describe actual states and transformations; they are not a new production data format or admission token. [S01–S04]

## 1. The objects being related

Fix one successful atomic strict compilation. Let K be its actual final prepared Core environment, D its ordered prepared declarations, I the original IR returned by its one erasure call, and J the JavaScript emitted from that same checked I through the pinned TypeScript compiler. Let O be the retained actual source/module ordinals, batch member Core identities and roles, normalization plans, and worker/public syntax and spans.

The atomic path supplies these concrete objects; it does not prove their semantic correspondence. The relation must use K, D, I, and O from that path. Re-elaborating a synthetic replacement declaration, looking up a similarly printed name in another environment, or attaching an unrelated passing report cannot supply a missing premise. Existing origins do not retain a context snapshot for every expression. A source argument may reconstruct the mathematical correspondence by following the actual branch and scope transitions, without requiring such snapshots in production. [S07–S10]

Use a proof world W with the following components:

| Component | Meaning |
| --- | --- |
| Core declaration identity | A full `PsName` interpreted in K, together with its actual prepared batch/member role. |
| Core local identity | A frame and `Nat` ID in the actual local context; IDs are not globally unique across unrelated frames. |
| Type assignment θ | Each in-scope retained type parameter is assigned a supported closed runtime type, with the corresponding Core type interpretation. |
| Layout association L | The actual Core family, constructor, projection and recursor identities associated with their emitted owners and ordered retained fields. |
| Executable association B | The actual Core-local → emitted-local mappings and Core-local → IR-expression substitutions. |
| Call alignment Π | The actual Core telescope, erased type/proof positions, retained argument order, and original-IR parameter groups for the function being related. |
| Output reservations Q | Emitted names reserved without creating a Core local, and their lexical lifetimes. |
| Origin association O | The actual source/normalized worker/public associations retained by the successful frontend. |

W is a mathematical record used to formulate a source proof. Existence of a record that merely repeats desired conclusions is not evidence. Each component must be obtained from the actual source branches and must satisfy the obligations stated below.

### 1.1 Type and host domains

A relation is indexed by the supported runtime type τ and, on the Core side, the corresponding Core type A and alignment Π. Its domain is the six enabled primitive types, Array, regular non-indexed data, immutable structures, and supported functions with captures and top-level rank-1 type parameters. The IR model also contains optional scalar constructors and `unknown`; their presence in that datatype does not enable them in strict SH/1. The actual source, IR and target admissions determine the accepted domain. [S01–S03, S11, S20–S21]

The host domain is the one already declared by the enabled runtime contract and runtime-law review. In particular, it contains canonical scalar strings, ordinary dense source arrays, ordinary generated data objects, and related generated functions. It does not silently acquire proxies, accessors, externally mutated objects, cyclic foreign data, arbitrary JavaScript callbacks, altered built-ins, or foreign imports. Resource premises concern successful representable allocation and the pinned host behavior; they do not identify wall-clock time, memory, allocation order, physical stack use, or implementation step counts. [S05–S06]

### 1.2 Values

Write V^n_CI(W, A, τ; c, v) for the Core/IR value relation and V^n_IJ(W, τ; v, j) for the IR/JavaScript value relation. Here c is a Core semantic value in K, v an abstract IR value, and j a host value. A Core semantic value is interpreted independently of the eraser: a scalar, a value of an actual Core constructor, or a Core closure/declaration with its environment and telescope. No claim is made that calling bounded `psWhnf` computes this runtime semantics.

The scalar and data clauses are as follows. Constructor/field clauses refer to L, not to an equality of printed type names.

| Type | Core/IR interpretation | JavaScript representation clause |
| --- | --- | --- |
| Nat | The same mathematical natural number n. | `bigint` equal to n and nonnegative. |
| Int | The same mathematical integer z, including the native negative-successor interpretation. | `bigint` equal to z; sharing the Nat carrier does not merge the types. |
| Bool | The same Boolean. | The corresponding primitive Boolean. |
| Char | The same valid Unicode scalar value. | A canonical string containing exactly that one scalar, with the contract's conversion behavior. |
| String | The same finite Unicode scalar sequence. | Its canonical well-formed UTF-16 string representation; raw-position operations retain the contract's byte-position meanings. |
| Unit | The unique Unit value. | `undefined`. An array element whose value is `undefined` can therefore be a present Unit element. |
| Array α | The same finite ordered sequence of values related at α. | An ordinary dense array with exactly that length and related present elements, used immutably by the source semantics. |
| Structure S θ | The unique structure constructor applied to its ordered retained fields. | An ordinary generated object with the associated private brand and the prescribed fields, each related at its instantiated type. The private brand is representation evidence, not a source field. |
| Regular inductive F θ | One actual constructor C of F with its ordered retained fields. | The associated generated constructor/tag representation, with the same constructor choice and related fields. Constructor identity is owner-qualified. |
| Function (τ₁,…,τₖ) → τ | A closure/callable and the exact ordered group, related through Π and the call clause below. | A generated callable with the corresponding captured environment and call behavior; registered and direct optimized callables are distinguished in the machine relation. |

For an empty inductive F, there is **no constructor-value clause**: no closed constructed v or j is related at F. This does not authorize deleting evaluation of an expression of type F. Its computation can still diverge, abort in an explicitly considered extension, or be unreachable. An empty match first demands its scrutinee. A structure with one constructor and zero fields is different: its value relation has that constructor case, and its branded zero-field record is an actual inhabited value. Neither the empty-type argument nor its test evidence needs a fabricated native value of F. [S11, S15–S17, S20, S22–S23]

For rank-1 polymorphism, quantify over every supported θ satisfying the retained declaration's type-parameter scope. Type arguments choose relation indices; they are not extra runtime values or permission to introduce higher-rank runtime polymorphism. Ghost/type arguments on the Core side require the erasure independence obligation in §6. [S01, S12–S14]

### 1.3 A non-circular call relation with a shared interaction budget

The function clause is shared by ER-04, EV-04/05, Array.map/foldl, and TS-04. Use a finite natural-number **interaction budget** n. The independently defined Core, IR and host computations are observed through that budget; the budget does not alter their operational meaning or measure physical execution time.

A matched semantic function application consumes one unit immediately before entering the related bodies. In C_CI, this is the source/Core application group whose alignment with the retained IR group must be justified by Π. In C_IJ, this is an original-IR application, including an operation's prescribed callback invocation. The application rule is available only when the current remaining budget r is positive, and its bodies start with r−1. Callee and operand evaluation have already carried forward any budget they consumed. If r is zero at the next invocation boundary, the observation **cuts off before that invocation**: its already-observed demand prefix remains relevant, but no subsequent result, abort, callback or termination claim is imposed. A computation that terminates without reaching another invocation still has a value obligation at its current index, including index 0.

Write C^n for the relation between such computations started with budget n. It carries the remaining budget as part of the observation, rather than giving each subcomputation a new copy of n:

- If an observation terminates in a value after k matched applications, where k ≤ n, its residual budget is r = n−k and its results satisfy V^r at the declared result type.
- If a permitted abort is observed before cutoff, its declared category and specified payload are related at that observation, and the pending continuation is abandoned. Resource failures and out-of-domain diagnostic probes retain the separate treatment in §2.3.
- If the next related invocation is reached with residual 0, the relation compares the observed prefix and the corresponding invocation boundary. It makes no claim about what happens after that cutoff.
- Operands, initializer/body sequences, selected branches and callback sequences share one residual budget. After a subcomputation returns with r, its continuation starts with r. Returning from a callback or nested runner invocation returns that residual to the suspended outer computation; it never resets the allowance.
- Previously obtained values and environments may be weakened from their earlier index to the current smaller one. This requires the downward-closure property of the V/E/C definitions; it is not permission to regenerate observation budget.

The value and environment indices use that computation relation:

- At index 0, a function must have the right group, actual structural capture edges/world identities, and permitted callable form; no semantic relatedness of captured values or future application-result claim is made.
- At index n+1, for every j ≤ n and every tuple of arguments related at the ordered parameter types at index j, the related function bodies, after the invocation's one unit has been consumed, satisfy C^j. The arguments and captures use that same residual index. Entering C^j is the consequence of the invocation's charge, not a second charge or a fresh allowance for each nested call.
- A returned function is related at its **result function type** at the residual result index, and a subsequent application consumes from that residual. A group of two parameters and a group of one parameter returning another function are different judgments.
- Data relations at each index use finite structural recursion over the actual data. The computation relation and the function clause must be interpreted together; one may not assume “all calls preserve semantics” in order to prove that the closures making those calls preserve semantics.

Write E^n for pointwise V^n relatedness of the associated environment entries. W and the index-0 function clause record actual identities, callable forms and capture edges only; they do not assume semantic relatedness of captured or global values. For V^(n+1), every captured environment required by its executable association is related at each E^j with j ≤ n. Thus E^n → V^n → E^j/C^j decreases the index on a function edge, including recursive/global closure edges; finite data edges use structural recursion. C^n is defined over independently given operational computations and budgeted observations, with terminal results in V^r at the **remaining** budget r. V^n can require only lower-index function behavior, even though C^n can return a value at V^n when no interaction is consumed. Downward closure follows by induction on the index and the finite data structure: lowering the initial budget either retains a shorter licensed observation with correspondingly weakened results or reaches cutoff earlier. This is an algebraic property of these definitions, not an implementation-preservation theorem.

For example, a higher-order body `g(Unit)` observed with budget 0 stops before applying g. It need not return equal Booleans merely because its two g values satisfy the structural function clause V^0. At a larger budget, the call consumes one unit and uses g's lower-index behavioral clause. Requiring an exact result after that unlicensed index-0 invocation would invalidate the intended compositional argument.

The general claim requires C^n for every n, together with divergence preservation/reflection or a separate sufficient termination argument for the admitted domain. For a terminating computation with finitely many logical applications, an arbitrarily larger initial budget can leave any desired result index after those applications. Finite-budget observations alone do not establish absence of infinite silent implementation stuttering. Construction of the complete simulation, its progress/cutoff correspondence, and that adequacy obligation remain open.

The interaction index is a proof device. One invocation's wrapper, `__ps$invoke`, registry dispatch, generator entry and any inner `__ps$run` are administrative realizations of that same semantic application, not separate charges. Constructor factories and let/match IIFEs introduce no new IR application event. Conversely, a count/tail loop iteration that implements an original-IR recursive application must account for that logical application even when JavaScript makes no physical call. Private helper lookup, eliminated bookkeeping and continuation scheduling may be silent. Order obligations concern the identified runtime operands, selected branches and related callback invocations; optimizer arguments must establish the matching and explain which internal steps are silent. This definition neither equates V8 instruction counts nor assumes that an optimizer's matching has already been proved. [S02–S06]

On the Core side, C^n_CI requires a separately justified source/Core evaluation interpretation and Π. Core β/ι equations and native primitive meanings are useful premises, but kernel definitional equality and bounded meta reduction do not by themselves fix a runtime demand schedule or validate regrouping. In particular, a recursor's induction-hypothesis demand cannot be defined to match the lowerer and then used as its proof. That adequacy obligation remains explicit in §6.

## 2. Environments, grouped application, and errors

### 2.1 Environments and closure extension

Let ρC, ρI, and ρJ be Core, IR and host environments. E^n_CI and E^n_IJ are lexical, type-indexed environment relations at observation index n.

For an executable local association (frame, id) ↦ x, the actual local declaration supplies A; θ and the type-erasure association supply τ; and the values obtained from ρC(id), ρI(x), and ρJ(x) satisfy the corresponding value relations V^n_CI and V^n_IJ. An IR closure captures the environment in which its lambda is evaluated. Extending a call frame adds the complete ordered parameter group, with each actual argument already evaluated. Binding a new x affects the body, not the environment used to evaluate its initializer.

For a substitution association id ↦ e in `runtimeExpressions`, the required clause is different: the Core meaning at id is related to evaluation of e in the corresponding IR environment. This is not necessarily a stored IR value, and duplicating a syntactic occurrence of e can duplicate a demanded computation. Induction-hypothesis reconstruction therefore needs a computation/demand argument, not just a variable lookup argument.

The .fvar branch actually looks up `runtimeExpressions` first, then `runtimeLocals`, then reports an erased/type-local use or an unknown local. An IH ID may intentionally appear both in `erasedLocals` and in `runtimeExpressions`. The expression substitution wins. An invariant requiring those lists to be disjoint is false for this implementation. Ordinary erased type/proof locals have no executable clause merely because an IH does. [S12, S14]

Global relatedness uses the Core identity ↦ output-name association built from the actual runtime prelude and prepared declarations. The JavaScript lexical binding must denote that global, not a shadowing local of the same spelling. For positive-arity declarations, the related callable exists with its registration/optimized implementation in the module environment; for zero-arity declarations, the related result is initialized in declaration order. Self-reference and earlier-global restrictions are part of the actual target admission, and their relation to Core identity is part of ER-09/TS-01/TS-08. [S13, S21, S23]

### 2.2 Application alignment

A Core application spine is ordered. Opening its actual telescope classifies each supplied operand as retained runtime, retained type index, or erased proof. The retained runtime domains are recorded before that operand's substitution advances the telescope. A call alignment Π records this actual selection and the resulting groups. It does not assert that any regrouping preserves semantics.

At the IR level, `call fn typeArguments [a₁,…,aₖ]` demands fn once, then the arguments from left to right, and then applies exactly that group. Each demanded subcomputation passes its residual interaction budget to the next; the final invocation consumes one unit from the budget that remains, as in §1.3. Type arguments instantiate type indices. There is no implicit JavaScript currying rule in the IR semantics. Exact group typing and scope checking are established separately from semantic correspondence. [S11, S14, S20]

The implementation contains three distinct eta-related transformations:

| Path | Actual transformation | Required semantic premise |
| --- | --- | --- |
| Missing-argument completion, `psEraseFinishApplicationWithFuelWorker` / capture helpers | Opens remaining runtime binders and produces a lambda. Computed supplied callee and operands are captured in typed outer lets, in callee/operand order. Type/proof operands are omitted by the same telescope classification. | The Core application prefix and the retained partial closure have the same already-demanded computations and capture meanings. Variables/literals skipped by capture already denote immutable values. |
| Result-arrow exposure, `psErasureEtaFunction` | For an already nonempty parameter list with function result, appends new parameters to that list and places `call body [] extraVariables` inside the expanded lambda. Runtime-lambda lowering also concatenates directly nested IR lambdas. | **ER-ETA-GROUP:** alignment of the Core function's curried/grouped use and the expanded runtime group, including when a function-valued body is demanded. Ordinary extensional eta equality does not establish arbitrary call-by-value demand equivalence. |
| Backend eta inlining | A recognized call with no type arguments and only suitably fresh variable arguments is pushed through the supported lambda/let/if/match callee forms and becomes exact zipped parameter lets. | The recognizer's side conditions, lexical/namespace non-capture, exact group, initializer scope, and unchanged callee-control demands imply equivalence to the general call path. |

The first repair does not prove the second rule. The backend rule does not justify changing the source-to-IR call convention. Empty parameter lists are not expanded by `psErasureEtaFunction`. All three rules must use the same V/C/environment relation. [S13–S14, S22–S23]

### 2.3 Result values, refusals, aborts, and resources

The result relation distinguishes the following cases:

| Case | Treatment |
| --- | --- |
| A value of source `Except E A`, including `Except.error e` | An ordinary related data value. This is how many compiler functions report refusal. It is not a thrown JavaScript exception. |
| A compilation-stage error, failed admission, or compiler fuel exhaustion | A result of the compiler's own operation, outside a successful-compilation preservation premise. Its specified diagnostic/refusal behavior has its own conformance obligations. |
| A runtime abort explicitly admitted by the compared semantic domain | An aborting outcome. Its permitted category and any specified message/value are related; later operands/continuations are not evaluated. The domain must name such aborts explicitly. |
| Defensive bounds/tag/empty-match throws reached from malformed or out-of-domain host input | Outside the canonical typed source value relation. Their existence cannot recover a missing source proof or provide a value of an empty type. |
| Foreign throwing-callback/first-fault probes | Diagnostic extensions useful for testing a particular demand path. They do not enlarge the admitted source effect or FFI domain. |
| OOM, stack exhaustion, timeout, and failed allocation | Resource failures governed by existing host/resource premises. They are not silently added to the source semantic error alphabet. |

The IR has no try/catch/finally expression. The generator runner propagates a host throw outward and abandons pending frames; it does not inject `.throw` into suspended generators. An abort-only relation fits this path. It would be insufficient for a language with source-visible handlers, finally blocks, or arbitrary foreign effects; those features are not introduced here. Exact JavaScript stack traces and allocation schedules are not observations of this contract. [S05–S06, S11, S23]

Proof-required Array.get/set remain restricted to the source proof/provenance or separately established bounds contract specified by SPEC. The emitted guard has useful out-of-domain refusal behavior, but a check that throws when a bound is invalid is not the erased proof's correspondence argument. String raw-position domains retain their full specified Nat/byte-offset behavior, including invalid or huge raw positions where the contract defines a result; no safe-integer cutoff or new validity condition is introduced here. [S01, S05–S06]

## 3. Original-IR evaluation rules

These rules define the abstract IR computation used by the shared relation. They cover every one of the eleven `PsVerifiedIrExpr` constructors. They are not an executable evaluator and do not claim that emission has already been proved to implement them. Types and layout references are checked against the same I and θ.

For a strict operand sequence, evaluate from left to right in the current environment, retaining the values already obtained. In the budgeted observation, each operand receives the preceding operand's residual budget; earlier values and environment entries are weakened to that current index. An abort/divergence of an operand prevents evaluation of later operands, and a cutoff imposes no claim about their subsequent evaluation. Lambda bodies and unselected alternatives are not evaluated while constructing a closure or selecting another branch. The same residual threading applies to every sequential context below, including let initializer/body and intrinsic callbacks.

| IR constructor / row | Evaluation rule and binding scope |
| --- | --- |
| `literal` / EV-01 | Produce the indexed literal value. The accepted literal/type domain comes from admission and the runtime contract. |
| `var` / EV-02 | Read the nearest corresponding lexical binding, or the permitted initialized global. It is a value lookup, not reevaluation of a binding's initializer. |
| `intrinsic` / EV-03 | Use the operation-specific domain, operand-demand rule and value law in the enabled contract. Strict operands are evaluated once in order. Bool.and/or use their declared short-circuit demand. Array.map/foldl invoke related callbacks in the prescribed element/accumulator order. |
| `lambda` / EV-04 | Produce a closure over the current environment, exact parameter group, result type and body. Do not evaluate the body now. |
| `call` / EV-05 | Evaluate the callee, then its runtime arguments left to right; invoke exactly the checked group under the related call rule. |
| `letE` / EV-06 | Evaluate the initializer in the old environment. Extend the body environment with its resulting value under the declared name/type. Then evaluate the body. |
| `ifE` / EV-07 | Evaluate the Boolean condition once. Evaluate only the selected branch in the current environment. |
| `record` / EV-08 | Evaluate retained field expressions once in their checked order. Construct the structure value with the associated layout and fields. A zero-field record produces its inhabited structure value. |
| `projection` / EV-09 | Evaluate the target once and select the associated structure field. Relation requires the owner/projection-index-to-field correspondence, not only a matching property spelling. |
| `constructor` / EV-10 | Evaluate retained fields once in checked constructor order. Construct the owner-qualified constructor value. |
| `matchE` / EV-11 | Evaluate the scrutinee once. Inspect its related constructor choice, select the one corresponding alternative, extend that alternative's environment with the specified related fields, then evaluate its body. An empty family has no value alternative. |

For an empty match in an inference-only position, the eraser supplies an IR `letE resultName resultType matched (var resultName)`, where resultType is obtained from the actual Core motive applied to the actual major. The initializer rule still evaluates matched and hence its scrutinee before any result lookup. There is no successful empty-value construction hidden in this annotation. The backend's typed empty IIFE/throw is a defensive implementation path, and its adequacy on well-typed empty computations is part of the computation relation. [S14, S20, S22–S23]

The 43 first-order primitive laws and the two higher-order Array laws reuse the domains and formulas in RUNTIME_LAW_REVIEW and the enabled operation contract. This document supplies the shared relation that their callback and representation premises refer to; it does not duplicate or silently discharge those premises. Char has no separate original-IR literal constructor; its values can arise through the enabled operations and corresponding Core lowering. Native wrappers such as raw String positions must be related through their specified erasure/primitive interpretation, rather than treated as new primitive capabilities. [S05–S06, S11–S14]

### 3.1 Generator and optimized implementation states

For the general emitted path, relate a generator-machine state to an IR evaluation state with its pending continuation stack and current residual interaction budget. A request contains a callee and argument values already obtained in IR order. Its semantic application consumes one unit; a registered callee pushes the corresponding generator implementation, while an unregistered permitted direct callable is invoked directly. Returning supplies the result and residual budget to the pending continuation. Intermediate WeakMap operations, wrapper entry and generator bookkeeping are silent and do not charge that application again.

Closures made by the general lambda path carry the current lexical environment and the registered implementation. Optimized top-level declarations and prescribed helper paths may be direct callables. Thus the relation must not require that every related function be present in the registry. Conversely, an arbitrary unregistered host function is not admitted just because the runner can call it.

Array.map/foldl can call public generated wrappers synchronously; such a callback may enter the runner while another runner invocation is suspended in the intrinsic. The simulation must compose those invocations with the related callback's captured environment and element/accumulator order. Every callback consumes from the outer computation's residual budget and returns its residue; the wrapper and nested runner do not create a new allowance. A theorem for a single flat runner stack does not automatically cover this reentry.

The backend's count-loop, tail-loop and eta recognizers each need a separate success-case argument to this same IR semantics. The unrecognized case uses the general path. Count-loop recognition by printed self-name still needs actual self-identity/non-shadowing; tail-loop tuple right-hand sides must be related in the old environment before simultaneous assignment. Pure-expression restrictions and alias/capture restrictions are real recognizer premises, not conclusions obtained from a passing IR type check. [S06, S21–S23]

## 4. The actual reachable erasure-scope invariant

### 4.1 Reachability and modes

Restrict Reach to scopes reached from `psEraseCoreModuleWithRuntimePrelude` on the actual atomic input, through the pinned preparation/erasure functions in the inventory below. This excludes an arbitrary caller-supplied `PsErasureScope`. The root scope has `psLocalEmpty`, empty local/substitution maps, the declaration-name index, and the built-in Nat recursor entry. Structure preparation precedes inductive preparation, and definition erasure receives the resulting actual layout maps. [S12–S17]

A scope's mode is mathematical information about its call site; no production mode tag is proposed. Output-only reservation is a subcase of executable lowering, and the normalizer syntax mode is an adjacent frontend boundary, rather than another runtime interpretation of an erasure map.

| Mode | What its names mean | Required restriction |
| --- | --- | --- |
| Executable | Core IDs are being opened to produce actual runtime local bindings or executable substitutions. | Relate emitted binders, lexical environments, and demanded expression substitutions. |
| Auxiliary type telescope | A runtime Pi is opened only to erase its type. Its local name is a sanitized auxiliary label, not an emitted parameter name. | Do not infer executable-name freshness or runtime capture from this scope. `runtimeExpressions` and `currentDefinition` are cleared in this branch. |
| Auxiliary layout telescope | Family parameters/constructor fields are opened to compute layout types and indices. Field labels are properties, not lexical executable binders. | Do not treat sanitized field labels in `runtimeLocals` as fresh emitted variables. Return to the outer maps after layout preparation. |
| Output-only reservation | A Nat or partial-application temporary is reserved while executable lowering continues. | Update the output-name set/count without allocating a Core ID or changing Core-local associations. |
| Normalizer syntax scope | Dummy locals track source-name shadowing during the syntax walk. | This is a `PsLocalContext` used before erasure, not an executable `PsErasureScope` or a source runtime environment. |

In particular, `psEraseRuntimeTypeWithFuelWorker` uses `psErasureSafeIdentifier`, not `psErasureLocalName`, when opening a runtime Pi. Constructor-field preparation also uses sanitized field labels. A blanket invariant saying “every name in every reachable `runtimeLocals` is a distinct emitted binder” would incorrectly reject the implementation's auxiliary scopes. [S12, S15]

### 4.2 Structural clauses established by source case analysis

The following clauses are source case facts for Reach. They describe actual data and control flow. They do not assert that the Core and IR values associated with those data are already semantically related.

**SC-1 — Local-ID ownership.** Every local-context declaration ID is below that context's `nextId`, and IDs in a single reachable context are distinct. Every ID added to a local/substitution map is the ID just returned by a push in that context. Proof: the root is empty; `psLocalPushBinding` and `psLocalPushLet` use exactly the old `nextId`, prepend that declaration and increment the counter; all erasure context replacements either preserve the existing context, use that pushed context, or restore an outer reachable context. Output-only reservations do not change it. This proves local ID freshness in these erasure frames; association of opened occurrences with the correct binder additionally uses SC-8 and O-SUB below. [S12–S18]

**SC-2 — Map roles and lookup precedence.** In these reachable scopes, type-local IDs are also recorded as erased; ordinary runtime-local IDs are not erased; IH expression-substitution IDs are newly pushed and recorded as erased. Expression-substitution lookup precedes runtime-local lookup in the .fvar branch. Proof: enumerate the definition, runtime-lambda, completion, layout-parameter, match-field and IH additions in §5; none reuses a pushed ID for a different role, and the type-Pi/layout reset branches only preserve or remove map entries. This establishes the data-role distinction, not ghost noninterference or IH meaning. [S12–S17]

**SC-3 — Output reservation accounting.** `declarationNames.count` bounds the number of distinct names present in `byOutput`. Initial index construction increments count for every inserted entry, including duplicates; the Nat-major and partial-capture reservation branches each insert one name and increment count by one; other scope transitions preserve that index/count or restore an earlier pair. These output-only insertions preserve `byCore`. The fixed-depth name index keeps collision buckets and performs exact `PsName` equality within a bucket; the hash is routing data, not identity or admission evidence. [S12–S14]

**SC-4 — The local fresh-name search.** Let U be the distinct names reported used by `psErasureLocalNameUsed`. Its size is bounded by `length runtimeLocals + declarationNames.count`. On a used base, the helper tests a sequence of base-plus-dollar-plus-Nat names with one more test than that bound. Under ordinary Nat numeral/string equality laws, those candidates are distinct, so a fresh candidate is found before the untested zero-fuel fallback is needed. This is a finite source argument for the local search, using SC-3; it is not a correctness theorem about arbitrary host representations of Nat/String. Some new call sites additionally recheck freshness and refuse if it fails. The unrelated global declaration-name helper has a fixed 4096-attempt `_overflow` fallback, so this argument must not be transferred to it; actual target admission must reject any resulting global collision. [S05–S06, S12–S14, S21]

**SC-5 — Initializers and newly generated binders.** Runtime let lowering erases the initializer in the old scope before pushing the let binding and opening the body. Partial-application captures reserve names only after all missing parameters have been opened; each computed supplied operand is placed in a typed outer let, with the callee first and the operands in order. The reverse capture list is wrapped from its head inward and then through its tail, restoring that outer-to-inner order. The new parameter variables are already values and remain inside the resulting lambda. These are exact tree-shape and order facts; runtime meaning additionally uses the evaluation rules and call-alignment proof. [S14]

**SC-6 — Computed Nat major.** A non-value Nat scrutinee is the initializer of exactly one outer Nat-typed IR let. The generated zero test and successor predecessor computation use its variable. Its emitted name is reserved before opening/lowering minors, without changing the Core context, `byCore`, or any Core-local map. A variable or natural literal uses the direct value path. This removes syntactic duplication of the computed major in that lowering; it does not prove the whole recursor/IH computation rule. [S14]

**SC-7 — Empty and zero-field data.** Empty elimination first builds the actual match, computes its result annotation from the actual motive/major, then emits the typed result let. No further Core body is opened under this output-only result binding; its body is just the result variable, and its initializer retains the old scope. The zero-field bare structure-constructor branch reuses the same actual constructor lookup/arity/field lowering as applied structure construction. Thus an inhabited zero-field record does not fall through to an ordinary global variable. These facts do not manufacture an empty inhabitant or prove every layout association. [S14, S16]

**SC-8 — Opening and closing syntax.** In `Core/Subst`, lifting increments bound indices at or above the cutoff; instantiation replaces exactly the index at depth with the depth-lifted replacement and decrements greater indices. Domain/value positions keep the depth; lambda/forall/let bodies increment it. `Core/Abstract` replaces exactly the selected free ID by the bound index at the current depth, traversing the same binder-sensitive positions. All eleven constructors of `PsExpr` are covered. The definition opener substitutes the same newly pushed fvar into its aligned type and value bodies. The standard inverse/meaning laws require the usual well-scoped/open-term hypotheses: abstraction does not independently repair pre-existing loose bound variables or arbitrary metavariable assignments. O-SUB states that remaining semantic premise. [S13–S14, S18–S19, S24–S25]

**SC-9 — Normalizer selections and actual origins.** Generalized/fixed binders and values are selected by a single traversal of the original typed-binder order with membership in the actual plan's ID list. Repeated IDs in that plan do not duplicate selected binders, and the origin need not falsify the plan by deduplicating it. Renamed source binders preserve the original binder kind and spans; synthetic names derive from actual IDs. The successful normalization path elaborates the actual worker, applies it to the selected original public binder values, checks that application against the original public type, then closes the original public binders. Actual worker/public associations are retained. This establishes which objects were used and their structural order; dependency legality, alpha meaning, state-call demand and public behavior remain N obligations. [S07–S10, S24]

### 4.3 Semantic strengthening still required

The useful invariant for a preservation theorem is Reach plus the following semantic clauses. Unlike SC-1–SC-9, their full preservation is **not established in this document**:

1. **Context/type validity:** Core types and opened terms are well scoped in their actual contexts, and the particular inference/reduction/classification results used by each erasure branch preserve the supported interpretation.
2. **Environment correspondence:** Executable `runtimeLocals` relate the correct Core values to IR locals; `typeLocals` realize θ; erased ordinary locals are observationally irrelevant; `runtimeExpressions` realize the specific related computations at IH IDs.
3. **Layout correspondence:** Each actual index entry denotes the actual Core family/constructor/recursor/structure, and its type arguments, retained source indices, projection indices and recursive-field flags give the value interpretation in §1.
4. **Current-definition correspondence:** `currentDefinition.name` denotes the actual current declaration, `typeArgumentsRev` reverses only the retained declaration type binders, and `runtimeParameters` has the actual retained declaration order. Replacing its identified major with the selected structural child yields the corresponding recursive computation.
5. **Scope of generated names:** Executable locals and output-only temporaries do not capture visible values or implicit emitted constructor-owner namespaces. Type/layout labels are checked in their own namespaces. Eta parameters generated after ordinary scope traversal satisfy the appropriate whole-body and namespace argument.
6. **Call/demand correspondence:** Telescope selection, direct nested-lambda flattening, completion captures, result-arrow exposure, recursor/IH substitution, and backend rewrites all satisfy the same Π and C relation.

The concrete smallest reusable proof object is therefore a derivation of this strengthened, mode-indexed invariant over the actual entry and transitions, together with the shared value/environment/call relation. It can be a source-level mathematical derivation. It does not need to be an additional serialized compiler output. A conditional lemma “erasure preserves semantics if every reachable scope is already semantically related” does not establish this invariant and cannot close ER-09 or the dependent rows.

### 6.1 What a source proof must actually do

For a rule such as runtime let, the proof has a concrete shape: use the actual initializer-erasure induction hypothesis in the old related environment; obtain related initializer values from C; use the fresh ID/name and O-SUB to extend the correct environments; use the body induction hypothesis; then apply the IR and emitted let evaluation rules. SC-1, SC-4 and SC-5 support specific steps, but do not replace either induction hypothesis or the representation/substitution facts.

For computed Nat elimination, SC-6 supplies one evaluation site for the major. O-LAYOUT and the primitive Nat laws establish the test/predecessor interpretation; O-CORE-DEMAND and O-SCOPE establish the selected minor/IH computation. A successful once-only host probe only observes its own invocation and cannot supply that universal IH argument.

For an empty family, the value case has no constructors. The computation case still proves that the scrutinee is demanded and that no result is manufactured. For a zero-field structure, O-LAYOUT has a real constructor case with an empty list of related fields. This prevents an empty-data proof from vacuously “proving” the inhabited record case or requiring an impossible native empty value.

For result-arrow exposure, the proof must start from the source/Core call behavior of the actual accepted function, not from the desired grouped IR type. If the necessary grouping/demand premise cannot be established for some accepted source shape, that is a concrete implementation/domain mismatch to resolve. This document reports the remaining proof obligation; it does not assert that an accepted counterexample has been demonstrated.

For the backend optimizers, a proof by successful recognizer cases is appropriate, provided it establishes every side condition used in its conclusion. A bare lemma whose hypothesis already says “the rewrite preserves behavior” is circular; a lemma over the actual structural recognizer plus independently proved reachable identity/capture premises is useful.

### 6.2 Evidence and completion boundary

A finite conformance receipt can bind exact source, prepared batch origins, original IR, emitted artifacts, native values and diagnostic traces. It cannot quantify over every related environment, type instantiation, structural child, function-valued argument, or callback. It also cannot turn a conditional hypothesis into an invariant. The exact-source cloud qualification remains mandatory implementation/conformance work with its own retained identities; this documentation review reports no execution result.

General source arguments need not be machine-checked to be an allowed assurance method under the present SPEC. They do need complete cases, precise admitted domains, a well-founded or otherwise sound shared simulation formulation, justified imported premises, and independent review. A future formal theorem would be stronger evidence with its own stated assumptions; no such theorem is claimed here.

A new persisted erasure association record is warranted only if a concrete necessary association cannot be recovered/proved from the actual path, or if it is selected as the implementation's assurance strategy and its correctness is established. It is not an additional SPEC MUST introduced by this document. The present foundation identifies the actual reachable-state argument available now and the specific semantic strengthening it still needs.
