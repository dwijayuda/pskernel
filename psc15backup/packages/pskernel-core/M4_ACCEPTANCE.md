# M4: provider readiness

M4 exposes the canonical kernel as an explicit native checking provider and
adds dual checking against pinned Lean 4.34.0. `lean434-wasm` remains the default
authority. Provider readiness does not promote a default or claim universal
equivalence outside the tested contract.

## Adapter and trust boundary

`host/src/Ps/Host/KernelCoreProvider/` converts canonical
`proofscript-checked-admissions` version 2 into KernelContract-v1 requests.
The wire contract admits safe definitions, theorems, and ordinary, indexed,
mutual, and nested inductive blocks. Other wire declaration forms fail closed.
The broader internal kernel API remains unchanged.

The adapter starts an empty session with the default provider capability (no
native evaluator), checks the compiler's current prelude, then admits each
request through `psKernelV1AdmitDeclaration`. Prelude replay defers only unknown
constant dependencies and fails if it stops making progress. Constructor and
recursor metadata are generated by admission, never inserted unchecked.
Neither the adapter nor its dependency closure calls Lean's official checker.
Lean compiles the native executable; PSKernel Core makes its checking decisions.

The 79-module portable semantic kernel is unchanged by M4. JSON, processes,
prelude adaptation, and host policy stay outside that closure. The archived
`pskernel-core.old3` selector remains separate.

## Using the provider

From `psc15selfhost`:

```sh
lake build psc_kernel_core_provider psc_kernel_core_provider_tests
cd lean-checked
lake build psc2_lean_checked_seed psc2_lean_kernel_provider
cd ..

# Keep the default authority and require agreement from native PSKernel Core.
node scripts/checked-build.mjs Main.lean --seed lean-checked/.lake/build/bin/psc2_lean_checked_seed \
  --out out.js --dual-check pskernel-core

# Explicit core selection; this does not alter the workspace default.
node scripts/checked-build.mjs Main.lean --seed lean-checked/.lake/build/bin/psc2_lean_checked_seed \
  --check --kernel pskernel-core
```

Windows executable names have the `.exe` suffix. The host resolves the current
`.lake/build/bin/psc_kernel_core_provider` or an explicit
`PSC_KERNEL_CORE_PROVIDER_BIN`; it never falls back to a different kernel.
Provider protocol, implementation, Lean target version/commit, and profile must
match. Identity metadata identifies the contract; it does not authenticate an
arbitrary executable supplied by the operator.

Dual mode accepts only when both providers accept the same admissions bytes.
Matching semantic rejections must identify the same declaration index.
Unsupported input, resource exhaustion, unknown internal failures, wrong
identity, process exit, invalid response, timeout, and disagreement prevent
emission. The checked-build receipt binds both identities and the decision to
the admissions SHA-256. Receipts are audit records, not transferable proofs.

## Bounded acceptance gate

The `PSKernel Core M4 provider parity` workflow builds current native providers
and reuses the verified bundled Lean WASM artifact. It does not rebuild WASM.

- 21 common canonical request cases × 2 official reference runtimes = 42 comparisons,
  plus the current declared prelude extension against native Lean (43 total).
- Coverage includes large naturals, universes, binders, beta/let reduction,
  theorems, projection, ordinary/indexed/mutual/nested inductives, duplicates,
  unknown constants, bad types, loose variables, and late rejection.
- Typed resource/cancellation/declaration-limit tests and fresh-session tests.
- Host identity, malformed input, timeout, crash, invalid JSON, and dual-mode
  disagreement/inconclusive tests.
- Actual compiler-to-dual-provider-to-emitted-JavaScript execution, explicit
  core checking of ProofScript, and refusal to emit after dual rejection.

Each parity provider invocation has a 10-second timeout; the corpus has a
180-second total budget. CI has a 20-minute job bound including fresh builds.
The production core host has a maximum 60-second invocation timeout and a
16-MiB output limit. These are operational bounds, not semantic rejections or
new M3 speed claims. Native kernel operations retain the existing recursive
fuel policy (4096), rather than a global instruction counter.

The workflow uploads `m4-provider-parity` with commit, case names, decisions,
identities, admissions hashes, and elapsed times. It runs alongside the existing
portable, native workload-budget, cross-runtime, and compiler integration gates.
M4 acceptance requires these checks to pass for the reviewed revision.

### Known bundled-WASM scope difference

The current compiler's declared `UInt8.ofNat` extension is accepted by both
native Core and current native Lean. The bundled WASM snapshot predates this
extension and rejects the name as unknown. The gate records this limitation
separately and requires dual mode to block emission on that disagreement; it
does not count the differing outcomes as parity. Full current-prelude parity
with WASM therefore remains open. Refreshing the bundled WASM is deferred to
an explicit release/rebuild task. This is another reason default promotion
is outside this bounded M4 checkpoint.

## Release reproduction and promotion

The existing `PSKernel Core generated fixed point (manual)` workflow remains the
release reproduction path. It rebuilds the generated compiler/kernel, verifies
source and generated fixed points, and checks evidence. It is intentionally
manual; full fixed-point reproduction and full-library replay are not part of
this bounded M4 gate and were not run for this checkpoint.

Switching the default authority requires a separate explicit decision with the
deployment workload and release evidence specified. M4 makes that decision
reviewable without requiring an unbounded pursuit of performance parity.
